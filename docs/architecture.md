# Harnessa architecture

## Milestone 1 boundary

Harnessa is a self-hosted, single-organization modular monolith. `apps/api` owns HTTP, identity, authorization, and persistence. `apps/api/harnessa/domain`, `services`, and `adapters` are package boundaries shared by the API and separately runnable worker process. Only the API is active in milestone 1; the worker entry point is deliberately inert until execution work is implemented. PostgreSQL is authoritative, Redis is available for later Streams transport, and the web app consumes server-generated OpenAPI contracts.

```text
apps/web ── HTTP + cookie auth ── apps/api
                                     ├── domain / services / adapters
                                     ├── PostgreSQL 16 + Alembic
                                     └── Redis 7 (future stream transport)
packages/contracts ◀── OpenAPI schema generated by API
infra/                 Compose and pinned container images
```

### Package responsibilities

- `apps/api/harnessa/domain`: lifecycle and domain rules, independent of HTTP and persistence.
- `apps/api/harnessa/services`: use cases shared by API and worker.
- `apps/api/harnessa/adapters`: provider, agent, storage, and runtime integrations.
- `apps/api/harnessa/api`, `auth`, and `db`: HTTP boundary, identity, persistence adapters.
- `packages/contracts`: generated TypeScript view of the API's OpenAPI schema; no handwritten duplicate API DTOs.

The extension interfaces reserved for later milestones are: LiteLLM model routing, OpenSpec CLI/schema discovery, ACP agent sessions/capability negotiation, AG-UI event projection/SSE, Harness² adapter, and content-addressed artifact storage with an optional S3-compatible implementation. No provider or GitHub connection is started by this milestone.

## State and contracts

The canonical task stages and independent run statuses are server-owned enums in `harnessa/contracts.py`; `domain/lifecycle.py` guards legal transitions and expected versions. Tasks persist a return stage for clarification and harness-probe branches. Durable event envelope fields include event/schema version, organization/project/task/run scope, aggregate sequence, actor, occurrence time, correlation/causation IDs, and payload. Errors expose stable `code`, `message`, `request_id`, and structured details. Identity and authorization carry organization and project roles. Specification revision and artifact metadata contracts include immutable revision/hash/base/policy references and checksum/size/retention/redaction metadata. `adapters/protocols.py` defines typed integration boundaries for LiteLLM, OpenSpec, ACP, AG-UI, Harness², and artifact storage without starting external integrations.

For mutating API calls, clients send a fresh `Idempotency-Key` (up to 200 characters). The API scopes keys to the authenticated user, hashes canonical JSON plus operation identity, replays the original status/body for a matching retry, and returns 409 if a key is reused for a different request. Optimistic task updates in later task endpoints must send the observed version in `If-Match`; stale versions return 409 `version_conflict` with current version in `details`. This milestone has no task mutation endpoint yet.

## Identity and access

FastAPI Users provides maintained password hashing and cookie authentication. Bootstrap is available only while the user table is empty and requires the out-of-band `BOOTSTRAP_TOKEN`; a PostgreSQL advisory transaction lock makes the first-admin check one-time under concurrent requests. Passwords require at least 12 characters. The authentication cookie is HttpOnly, SameSite=Lax, and Secure in production. Login and all other mutating requests require exact allowlisted Origin and a double-submit CSRF token (bootstrap instead requires its out-of-band token). CORS allows only configured origins. Downstream authorization consumes the internal `Identity` and membership contracts, not provider token claims; a future OIDC adapter must map issuer/subject to the same internal user and membership records.

Organization memberships determine organization roles. Project memberships further scope operators and other project roles; an administrator can manage projects in the installation's organization. `Identity` and `AuthorizationContext` are internal contracts; authorization is resolved from local memberships. The future OIDC adapter maps the verified `(issuer, subject)` pair to an internal user, then uses the same membership lookup. Provider role/group claims are never authority; local membership and project scope remain authoritative. Repository registration accepts an exact target identifier from `REPOSITORY_TARGETS`; it does not connect to GitHub, clone, or scan a repository. Production startup fails closed unless a 32-character secret, bootstrap token, and Secure cookies are configured.

## Database

Alembic revision `0001_foundation` creates organizations, users, organization memberships, projects, project memberships, repositories, tasks, and the idempotency request ledger. Records use UUID identifiers and timezone-aware UTC timestamps; uniqueness is scoped to the owning organization or project. `alembic_version` tracks migration state and organizations carry a schema version. Later run/session/checkpoint, lease, event/outbox/inbox, specification revision, question/answer, agent profile, verification, review/PR, model deployment/budget, harness/evaluation, and artifact entities are reserved for their corresponding milestones; this milestone does not create placeholder tables.

## Deployment and security boundaries

`infra/compose.yaml` boots PostgreSQL, Redis, API, and Next.js. Image references include immutable registry digests. `.env.example` contains only local placeholders. No engine socket, operator home directory, SSH key, model credential, or GitHub credential is mounted into an agent. There is no agent execution yet. Artifact and GitHub integrations remain disabled until explicitly configured in later milestones.
