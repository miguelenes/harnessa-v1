## Deterministic implementation evidence

| Area | Evidence and result |
|---|---|
| Immutable artifacts | Strict `skills/<slug>/SKILL.md` path/frontmatter/size validator; SHA-256 and CAS storage; separate imported, operator-authored, and generated provenance; task/repository/project/organization scope fields; source run/evaluation links; dependency/tool declarations; license, trust, confidence, expiry, compatibility and conflict metadata. ORM immutable-field guard and PostgreSQL trigger protect content/provenance while lifecycle state remains mutable. |
| Scope and authorization | Import API supports four scope types. Task imports bind to one task and cannot be activated across task boundaries. Organization import and promotion require an organization administrator. Repository/project/organization scoping is enforced during candidate selection and active skill loading. Cross-scope candidate collisions are checked before evaluation and promotion. |
| Imported route compatibility | Imports bind to an enabled route alias and a canonical digest of its enabled deployment identities, capability declarations, context limits, and price revisions. Grouped evaluations require the exact alias and digest; active skill loading compares current route capabilities and marks drifted artifacts stale. |
| Conflict lifecycle | An administrator can idempotently reject a complete overlapping candidate group with a rationale. Candidate status history remains visible, an append-only resolution record captures the actor and affected IDs, and the selected bytes must be reimported as a new version before evaluation. |
| Candidate derivation | Self-reported lessons are ignored. A skill candidate must come from an actual changed, schema-valid file in a successfully composed tree, with matched probe evidence, a bound composed source run, and a passing holdout receipt. Exact selected skill bytes are excluded from duplicate candidate derivation. |
| Editable surface | The adapter validates the pinned OpenCode component paths, rejects immutable policy files, disables subagent edits, and validates every `SKILL.md`. Declared tool names do not grant capabilities. The manifest keeps Harnessa host policy separate from editable Harness² components. |
| Evaluation manifest | Schema version 2 binds the task subset, common bases, task/specification revisions, route/deployment/pricing policy, Harness² and policy revisions, executor/image/tool revision, selected skill version and exact digest, budget bounds, and evidence references. Unconfigured seed, benchmark/judge, MCP-grant, and artifact values are represented explicitly as `null` or empty lists. These unknowns block claims that a live hidden evaluation occurred. |
| Evaluation and lifecycle | Candidate skills are materialized only into candidate/composed harness trees after digest, schema, CAS, path, and symlink checks; the baseline is unchanged. Promotion requires a matching multi-task evaluation, all matched/composed children succeeded, exact candidate versions in holdout manifests, a passing manifest-bound receipt, and known costs. Promotion and rollback preserve immutable versions and append decision evidence. |
| UI | Harness Studio shows provenance, scope, license, conflict, declared tools, dependencies, artifact link/hash, compatibility drift, expiry, and lifecycle actions. Evaluation Center can freeze an exact candidate skill into a bounded grouped manifest. |
| API contract | OpenAPI regenerated through the repository's pinned `openapi-typescript` 7.13.0 generator; generated contracts include skill import scopes and `skill_experience_id`. |
