- Added bounded per-route attempts, `Retry-After` handling, deployment cooldowns/circuit breakers, explicit fallback order, interactive capacity reservations, configurable probe overflow, pre-dispatch spend/token reservations, atomic budget accounting, stale-reservation reconciliation, and reservation heartbeats during streamed responses.

Prompt and completion bodies are not written to the ledger. Provider response details and credentials are not copied into errors or logs.
- For a stream, fallback can happen only before the first response line. After streaming starts, a failure is surfaced as `model.error`; no workflow or tool effect is replayed. The worker uses an unconfigured execution adapter, so it does not call the model automatically.
- Updated the `ModelRouter` extension contract, architecture, compatibility record, Compose setup, README, and generated TypeScript contracts.

## Live compatibility check: pending

No paid service was provisioned, no provider key was supplied, and no live model request was sent. To perform one explicitly authorized check after choosing a provider/model:

1. Put the provider key in the local, untracked `.env` only (for example `OPENAI_API_KEY=...`). Never place the value in chat, source files, or the API account request.
2. Add one local LiteLLM entry to `infra/litellm/config.yaml`. Set `model_name` to the deployment's `proxy_model`, set the provider/model, and use `api_key: os.environ/OPENAI_API_KEY` (or the matching provider variable). Restart LiteLLM with `podman compose -f infra/compose.yaml restart litellm`.
3. As an organization administrator, use `POST /ops/models/accounts`, `POST /ops/models/deployments`, `POST /ops/models/aliases`, and `POST /ops/models/pools/{pool_id}/routes` to register the matching route. Set a project budget with `PUT /projects/{project_id}/models/budget`. These endpoints store only the `env:VARIABLE_NAME` reference and declared price revision.
4. Sign in through the web UI, obtain the local `harnessa_auth` and `harnessa_csrf` cookies, and confirm the alias and project budget. Then run this one-request command with local shell variables set from that session:

   ```sh
   export API_ORIGIN='http://localhost:8010'
   export WEB_ORIGIN='http://localhost:3000'
   export PROJECT_ID='<project UUID>'
   export MODEL_ALIAS='<configured alias>'
   export AUTH_COOKIE='<local harnessa_auth cookie value>'
   export CSRF_TOKEN='<local harnessa_csrf cookie value>'

   curl --fail-with-body -sS -X POST \
     "$API_ORIGIN/projects/$PROJECT_ID/models/live-check" \
     -H "Origin: $WEB_ORIGIN" \
     -H "Cookie: harnessa_auth=$AUTH_COOKIE; harnessa_csrf=$CSRF_TOKEN" \
     -H "X-CSRF-Token: $CSRF_TOKEN" \
     -H "Idempotency-Key: live-check-$(date +%s)" \
     -H 'Content-Type: application/json' \
     -d "{\"alias\":\"$MODEL_ALIAS\",\"authorize_paid_request\":true}"
   ```

The live-check endpoint requires an administrator membership, a configured project budget, a unique idempotency key, and the explicit `authorize_paid_request: true` body field. It sends one small Chat Completions request through the same budget reservation and ledger path. The result remains pending until a user with provider credentials and spending authorization runs it.

## Limitations and next milestone prerequisites

- The deployment catalog and LiteLLM config are currently configured separately; `proxy_model` must match the configured LiteLLM `model_name`. The doctor verifies gateway readiness and catalog counts, but does not inspect provider credentials or send a model request.
- Prices and capability declarations are operator-provided metadata. They must match the selected provider deployment. Billing headers and provider usage are recorded when returned; missing usage is settled conservatively as estimated/unknown.
- A provider request that times out can have unknown provider-side billing. Each such attempt is recorded and reserved spend is conservatively settled. Retry/fallback latency is bounded by configuration but is not promised as a fixed duration.
- Short-lived scoped runner credentials, ACP execution, cancellation behavior of a concrete agent, tool orchestration, AG-UI projection, Harness² probe integration, and artifact persistence are later work. No tasks or artifacts are created by the model APIs in this milestone.
- A fresh checkout requires Podman or Docker Compose, network access for pinned images and package installation, local `.env` configuration, and a disposable `_test` PostgreSQL database plus Redis database 1 for integration tests. No paid services or real credentials are required for the automated checks.
