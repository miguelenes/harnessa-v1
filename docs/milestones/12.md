## Implementation evidence

- Upstream Harness² is pinned at `1cfe254e8d25b15f37048c3730134686abe60335` under Apache-2.0, with eight upstream component categories mapped through a product manifest.
- Five additive database tables store fixed project policy, task experiments, probe evidence references, scoped candidate experiences and append-only promotion/rollback decisions.
- Probe model calls use Harnessa's task/project budgeted probe pool and idempotency key. Candidate edits are validated against upstream's OpenCode surface, bounded, isolated beneath a candidate workspace, and checked for path escapes and named host-policy edits. Holdout-shaped context is rejected before dispatch.
- The ACP prompt now places repository and candidate harness guidance before a final immutable host-policy reminder; the added ACP regression test verifies the ordering and prohibited operations.
- Project API operations require membership; experiment creation requires an operator, HARNESS_PROBE task and ready frozen specification. Promotion and rollback require an administrator and the exact reviewed digest. Post-merge learning only produces an expiring `candidate` experience from a successful experiment and explicit evidence refs.
- Harness Studio reads the authorized project manifest, experiment history, probe diffs and experience evidence and offers reviewed promotion/rollback actions.
- The durable queue currently has no worker that runs a frozen task through baseline, candidate and composed execution. Experiments can remain queued; this is an acceptance blocker, and the upstream offline demo is not evidence of Harnessa task execution.
- The final review found the post-merge learning hook was hardcoded off; this was fixed on the branch and independently re-reviewed. A subsequent finding that verification feedback could follow the host-policy reminder was fixed in `dddb1d5`, tested, independently re-reviewed, and its review thread resolved.
