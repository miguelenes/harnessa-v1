### Changed-file sync follow-up (2026-10-23)

It resolves the last successful sync commit and diffs the current default branch against that ancestor, reading blob contents only for changed eligible files. Unchanged source records retain their last-content revision. Sync results expose whether the pass was incremental; a no-change repeat is idempotent. Status reports `indexed_revision` from the latest successful sync while `coverage` remains tied to the latest complete full-snapshot `coverage_revision`; the freshness field identifies when incremental work is newer than the coverage baseline. A missing baseline forces a full snapshot. `considered` counts deleted paths as well as changed and omitted files.

### Verified-run evidence follow-up (2026-10-23)

The former verified-run blocker is addressed in this follow-up branch. `verification_evidence` is a durable immutable result record scoped to organization, project, connected repository, task, run, attempt and fencing token. The trusted server-side `record_verification_evidence` port validates those IDs against durable Harnessa records, validates verifier identity, source revision, bounded criteria/summary and optional run-fenced artifact digest, rejects secret-like text, and enforces idempotency by verifier source record ID and canonical content hash. It has no public route and does not infer outcomes from scheduler status. The existing repository search path lexically includes only explicit `passed` evidence for the selected project and repository, then rechecks project membership and repository ownership before returning content. Citations reference the run/evidence ID, verifier source revision, and immutable content hash. Failed, manual-review and unverified records remain stored but are not searchable as passing evidence.

Evidence status is **offline fixture only** for the producer and retrieval behavior.
