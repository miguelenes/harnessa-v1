## Matrix result and limitations

The current integration suite passes its existing scenarios, and the LangGraph smoke suite demonstrates a narrow set of database-backed APIs. The full critical matrix did **not** pass on both runtimes:

- Current Harnessa has no durable question/answer authority or route, and the production execution adapter is unconfigured. Candidate answer/dispatch/effect checks use spike-only SQL fixtures; they do not count as Harnessa authority evidence.
- Neither side ran a process-kill fault at both sides of checkpoint commit, cancellation resource/process cleanup, database outage, or the exact timeout-after-accepted-effect schedule.
- LangGraph was not connected to Harnessa leases/fencing, domain-event replay, budget reservations, or effect-intent reconciliation. Candidate attempts cannot prove those controls.
- Candidate setup was tested fresh and repeatable through migration version 9. The package has no downgrade API; an older-schema upgrade plus rollback preserving Harnessa audit/effect rows was not demonstrated.
- The fixed 64-run workload was not executed. Its 16 human waits cannot be represented with current Harnessa question authority without substituting a synthetic pass. Therefore p50/p95 dispatch and recovery latency, database write/storage ratios, worker RSS ratios, and the required 20% custom-code reduction have no valid paired result. The candidate test suite's 0.65 second runtime is not a workflow benchmark.

These are explicit NO-GO findings under the prompt's conjunctive gate, not claims that the candidate is unsuitable in every future architecture. No threshold was relaxed after candidate execution. Harnessa remains authoritative and its current scheduler remains selected.
