## Upstream Harness² reference checked for the fixture boundary

The repository had no Harness² submodule or checkout. For a reproducible M11 fixture contract, upstream `google-research/harness2` was inspected at commit `1cfe254e8d25b15f37048c3730134686abe60335` (the `main` head observed on 2026-10-23). At that commit its source tree contains `harness2/core/{recursion,ledger,runmark,report}.py`, `harness2/benchmarks/{jobbench,lab,workbuddy}.py`, and `harness2/substrate/{opencode,codex}.py`; its README documents OpenCode and Codex executors, JobBench (`jb`), LAB (`lab`), WorkBuddy-Bench (`wb`), and parallel/sequential recursion. Its run markers use a versioned `.adapt_complete` JSON file and include run ID/time and a harness fingerprint; its Python ledger records task ID, mode, `k`, model spend, and rollout/session labels. The output root is benchmark-specific (`runs/lab`, `runs/jb`, or `runs/wb/<subset>`), not a single cross-benchmark result schema. M11 therefore defines a Harnessa-owned fixture manifest and hashes every imported file rather than assuming an upstream universal export manifest.

This is a source-interface inspection, not a Harness² installation, executor smoke, benchmark run, license review, or provider-backed acceptance. No upstream code, benchmark, dataset, credential, or result artifact is added to Harnessa in M11. M12 must recheck this pin and the selected benchmark's license, setup requirements, exact result paths, executor support and data revision before enabling a real adapter.

## M11 implementation and acceptance evidence

### Read-side contract and adapters

`GET /projects/{project_id}/evidence` is a project-membership-protected projection over existing PostgreSQL source rows. It accepts `task_id`, `run_id`, `source`, `revision`, `cursor`, and a bounded `limit` (1–100). Membership is checked before reading; task and run IDs are checked against the selected project. Cursors encode the last `(recorded_at, source_record_id)` pair and are URL-safe. The TypeScript client is generated from the local FastAPI OpenAPI schema. The API exposes metadata and hashes only: model prompt/completion bodies, webhook payload JSON, tool arguments/results, and artifact bytes are omitted.

The version 2 `CoreEvidenceEnvelope` supplies typed known/unknown/redacted identifiers for organization, project, repository, task and revision, run/attempt, model request, tool invocation, webhook delivery, Git effect, artifact, evaluation, harness revision, and skill revision. Older envelopes remain valid with unknown defaults for newly added links. Native rows retain their existing IDs and authority. The response joins retained domain events, task transitions, runs, every model ledger event/attempt, artifact metadata, verification executions, GitHub effect intents and reconciled GitHub objects. Project-wide reads additionally include metadata-only direct MCP audits and webhook inbox receipts for linked repositories; task filters include webhook receipts only when a linked task/repository relation exists. ACP tool call IDs are extracted only from their redacted domain-event payload field.

Model summaries keep gateway billed spend, estimated spend and usage certainty distinct; provider-reported actuals are `unknown` unless the source reports them. Null is not coerced to zero. An unresolved model usage is marked `pending_gateway_usage`; failed webhook receipts are marked `retryable`; artifact hashes are marked `checksum_unverified` until a byte-level integrity check is run; GitHub objects are marked stale when their head differs from the latest run source revision. The existing M10 webhook retry/current-state reconciler remains the only GitHub repair path, and replay remains keyed by the App delivery ID. Late LiteLLM spend-log observations are imported through a bounded, project-authorized endpoint. Each source observation has a durable idempotency record; unmatched records remain retryable with a scheduled backoff timestamp, ambiguous matches remain visible, and a unique match appends a `usage_reconciled` ledger event without rewriting earlier events or replaying model requests. Gateway billed and provider-reported amounts occupy separate columns and remain unknown when absent.

M11 defines `Harness2ImportFixture` and `validate_harness2_fixture` as a deterministic, untrusted boundary for M12. The fixture pins the upstream source revision, benchmark/task, executor, recursion mode, `k`, seed, result, candidate/judge revision values, and exact relative artifact paths, sizes, and SHA-256 digests. The validator rejects path traversal, duplicate paths, trust elevation, missing/extra files, and checksum or size mismatches. It does not execute Harness², persist a score, or promote imported results to Harnessa task outcomes.

### Retention, export, and recovery contract

The provenance view is assembled from existing source-authoritative rows plus the durable gateway usage import receipt table. A new additive Alembic migration adds provider-reported spend, the reconciliation ledger event type, and source-observation retry state. Domain events are omitted after their stored retention deadline; the source rows remain governed by their existing per-source retention/deletion rules. An export must preserve row IDs, project/task/run references, event sequence, content hashes, source revision, and the artifact CAS volume together. Restore verification must compare artifact bytes with their declared SHA-256 and verify project-scoped foreign-key joins before serving provenance. Schema changes are additive and versioned; consumers ignore unknown links and retain unknown values instead of inventing defaults. Rollback downgrades this additive schema after stopping writers; historical source rows and ledger events are never rewritten, and deployments must retain gateway import exports before downgrade because the new receipt table is removed.

### M11 acceptance state

Deterministic coverage validates cursor parsing, project-route authentication, known-versus-unknown envelope behavior, exact Harness² fixture checksums, rejection of path traversal/trust elevation, retryable late-usage imports, unique matching, duplicate-import idempotency, and sparse revision pagination. TypeScript API types are generated from the app's local OpenAPI document. The task inspector shows source, recorded time, revision, hash, import status, reconciliation status, and stale state; Browser Harness confirmed the unknown-spend labels and the `checksum_unverified` to `verified` integrity transition with its audit event. The final `pnpm test` acceptance passed on disposable PostgreSQL 16.13 and Redis 8.10.2. A live provider and authorized GitHub repository are not configured, so those are fixture-based adapter checks rather than live external acceptance.
