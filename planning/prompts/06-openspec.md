## Fifth: create the local push-to-merge CI/CD pipeline

Add the required GitHub Actions workflow(s) so every branch push and pull-request update, including pushes to `master`, receives the full required CI result on the repository's local self-hosted runners. Route jobs only to `[self-hosted, linux, x64, harnessa-local]`; if no matching runner is online, leave the run queued and block review/merge rather than falling back to GitHub-hosted runners. Run the dependency/install, lint, typecheck, build, complete test, parallel-safe test, and 85% coverage gates from above. Pin every third-party action to a full commit SHA. Bind status and review results to the exact commit SHA, serialize automated changes per branch/PR, and do not silently cancel or mark a required check successful when it did not run.

Require changes to enter `master` through a pull request with the required CI statuses and the repository's branch-protection rules. After CI passes, open or update a PR targeting `master` for each eligible branch push that does not already have one, then start the configured code-review agent on that exact PR revision. The agent must report evidence-backed findings and apply in-scope fixes to the PR branch; every agent-authored commit triggers the complete CI gate and another review of the new head. Limit the repair loop to three rounds per PR; if findings or failures remain, leave it unmerged and report them. Auto-merge to `master` only after the final review has no unresolved blocking findings, the exact head has passed every required check, and all branch-protection requirements are satisfied. Never force-push, push directly to `master`, bypass required approvals/checks, or merge on a stale review. A post-merge push to `master` runs CI verification but does not start a second review/merge cycle. If the runner, review agent, repository permissions, or branch-protection configuration prevents this flow, leave the change unmerged and document the precise blocker and operator action.

Keep self-hosted execution isolated: use a clean, ephemeral local runner for one job, under an unprivileged account and a disposable VM or rootless container boundary where feasible. Never expose the host Podman/Docker socket or long-lived credentials to repository job code, and grant only the permissions needed by each job. Do not expose secrets to fork/untrusted code; require explicit maintainer approval before untrusted code can run on the local runner, and provide no secrets or persistent host access to that job. Use short-lived, repository-scoped write authority for agent fixes/merge. Keep any production deployment behind an existing documented and authorized target; the required milestone flow ends at a protected merge to `master`.

Validate workflow syntax locally, but do not treat local emulation alone as proof. Record workflow files, runner labels/isolation, exact check names, branch-protection state, per-push evidence, review/repair/merge evidence, and any external setup in `docs/milestones/06.md`. A passing workflow parser or `act` run is not evidence that a real push was checked by the local self-hosted runner.
